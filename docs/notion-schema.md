# Notion DB 구성 (v2, 검토용 보드 생성 완료)

고객사가 쓰는 기존 관리 페이지(의뢰인 기본정보 · 이벤트 관련정보 · 1차/2차 상담 내역 · 결제)의 **항목 구조**를 따라 만들었습니다.
기존 페이지와 같은 이름을 써서, 직원이 보고 옮기거나 나중에 연동할 때 헷갈리지 않게 했습니다.

DB는 세 개입니다.

```
고객 ──< 이벤트(의뢰) ──< 상담 이력
 1명      의뢰 1건          통화 1건 (1차, 2차 …)
```

## 1. 고객

| 속성 | 종류 | 누가 채움 | 기존 페이지 항목 |
|---|---|---|---|
| 의뢰인 | 제목 | 코드 | 의뢰인 |
| 고객 구분 | 선택: 개인 / 기업 | 코드 (기본 개인, 회사·단체 있으면 기업) | (신규 요청) |
| 표시 | 다중 선택: 접수 경로(업체 설정 `channels`) + B 블랙리스트 | 코드/사람 | 접수 경로는 분명할 때 봇이 덧붙임(녹음 → 전화, 채널 상담 내보내기 → 메신저 채널, 그 밖엔 대화에 분명할 때). 지우지 않음. B는 사람만, B면 봇이 경고 (D24, D46) |
| 회사·단체명 | 텍스트 | LLM | 기업 고객일 때만 |
| 연락처 | 전화번호 | 코드 | 연락처. `010-0000-0000`로 정규화, **고객을 찾는 기준** |
| 추가 연락처 | 텍스트 | 사람 | 다른 전화번호만 (D40) |
| 전자메일 | 이메일 | 코드 | 전자메일 |
| 회원아이디 | 텍스트 | 사람 | 회원아이디 |
| 이벤트 | 관계형 → 이벤트 | 코드 | |
| 메모 | 텍스트 | 사람 | 코드는 건드리지 않음 |

## 2. 이벤트 (의뢰)

기존 페이지의 의뢰 1건 = 1행. 캘린더 보기(확정 일시 기준, D37)로 기존 ‘이달의 이벤트’ 화면을 대신할 수 있습니다.

| 속성 | 종류 | 누가 채움 | 기존 페이지 항목 |
|---|---|---|---|
| 제목 | 제목 | 코드 | `의뢰인 · 테마 · 희망일` |
| 고객 | 관계형 → 고객 | 코드 | |
| 의뢰일 | 날짜 | 코드 | 의뢰일 |
| 이벤트 테마 | 선택 | 코드/LLM | 상품이 정해지면 업체 설정의 상품 테마, 아니면 LLM (D36) |
| 희망 이벤트 | 선택 | LLM/코드 | 관리 페이지 상품명. 종류가 여럿인 상품 묶음을 종류 없이 말하면 비워 두고 확인 필요 `희망 상품` + 추가 질문 (D45). 상품명과 고객 안내 이름은 업체 설정 `agent/business.json`에서 관리하고, 코드가 안내 이름을 상품명으로 바꿈 (D23) |
| 희망 장소 | 텍스트 | LLM | 장소명 또는 주소만 (메모는 추가 질문으로) |
| 지도 링크 | URL | 코드/사람 | 직원이 보낸 네이버 지도 링크(열어서 장소 페이지로 이어질 때만), 없으면 네이버 검색 API로 장소가 딱 하나 확인될 때만 그 장소 검색 링크. 확실하지 않으면 비움. 직원이 직접 넣은 링크는 덮어쓰지 않음 (D30, D48) |
| 확정 일시 | 날짜 | LLM/사람 | 예약이 확정된 일시 (고객사가 만든 칸, 이전 이름 '날짜'). 통화에서 예약이 확정됐을 때만 봇이 채움, 아니면 사람 (D31, D37) |
| 특이사항 | 텍스트 | LLM/사람 | 현장에서 챙길 것 (고객사가 만든 칸). 봇은 덮어쓰지 않고 날짜와 함께 덧붙임 (D31) |
| 제휴 | 선택: 업체 브랜드 (agent/business.json) | LLM/사람 | 접수 브랜드. 인사말 등으로 분명할 때만 봇이 채움 (D31) |
| 희망 일시 | 날짜(시간 포함) | LLM | 이벤트 희망일시. 불완전하면 비우고 `확인 필요` |
| 희망 일시(원문) | 텍스트 | LLM | 통화에서 말한 그대로 (예: `12월 12일 저녁`) |
| 고객 예산 | 숫자(원) | LLM | 고객이 말한 예산 (이전 이름 '예상 금액'). 말하지 않으면 비워 두고 확인 필요로 표시하지 않음 (D35, D40) |
| 예약금액 | 숫자(원) | LLM | 상담에서 안내한 예약금 금액 (고객사가 만든 칸). 입금되면 사람이 결제 상태를 '예약금 입금'으로 (D30, D38) |
| 문의 및 신청사항 | 텍스트 | LLM | 문의 및 신청사항 |
| 이벤트 상태 | 선택 | 코드 → 사람 | 상담진행중 / 추후연락 / 이벤트진행예정 / 이벤트완료 / 이벤트취소 |
| 결제 상태 | 선택 | 사람 | 미입금 / 예약금 입금 / 완납 (D38). 봇은 읽기만 하고 자동 점검에 씀 (D41) |
| 결제 방식 | 선택 | 사람 | 온라인결제 / 카드결제 / 계좌이체 (D38) |
| 결제일 | 날짜 | 사람 | 결제일 |
| 확정 금액 | 숫자(원) | 사람 | 총 액 (이전 이름 '총액', D40) |
| 상담 이력 | 관계형 → 상담 이력 | 코드 | 1차/2차 상담 내역 |

- 결제 관련 항목은 사람이 채웁니다. 사각사각은 통화 내용에서 결제 정보를 확정하지 않습니다. 결제 대화는 상담 내역·전사에 남기고 계좌·카드번호만 가립니다 (D29).

## 3. 상담 이력

통화 1건 = 1행. 기존 페이지의 ‘1차 상담 내역’, ‘2차 상담 내역’에 해당합니다.

| 속성 | 종류 | 누가 채움 | 기존 페이지 항목 |
|---|---|---|---|
| 제목 | 제목 | 코드 | `11/06 의뢰인 · 2차 상담` |
| 이벤트 | 관계형 → 이벤트 | 코드 | |
| 상담 차수 | 숫자 | 코드 | 1차, 2차 … |
| 상담자 | 선택: 직원 명단 | 코드 | 이름만 받아도 직원 명단에서 맞춤(이름만 → 성까지). 명단에 없으면 새 선택지로 추가 (D25) |
| 상담 일시 | 날짜 | 코드 | |
| 상담 내역 | 텍스트 | LLM | 상담 내역 (요약) |
| 옵션 내역 | 텍스트 | LLM | 옵션 내역 |
| 옵션 가격 | 숫자(원) | LLM | 옵션 가격 |
| 후속 업무 | 텍스트 | LLM | |
| 다음 연락 시점 | 텍스트 | LLM | |
| 확인 필요 | 다중 선택 | LLM/코드 | 정해진 항목만: 희망 일시 · 희망 장소 · 예산 · 예약금 · 이벤트 테마 · 다음 연락 시점 · 고객 연결 · 이벤트 연결 · 기존 정보와 다름. 그 밖의 것은 추가 질문으로 (D34) |
| 추가 질문 | 텍스트 | LLM | |
| 검토 상태 | 선택 | 코드 → 사람 | 확인 대기 / 확인 완료 / 고객 연결 필요 (같은 고객인지 사람이 골라야 함, D39) |
| 입력 방식 | 선택 | 코드 | 녹음 / 전사 텍스트 / 대화(카톡·채팅 내보내기, 메모) (D40) |

**페이지 본문**: 근거(항목 · 근거 문장 · 녹음 시간, 녹음이면 그 구간 클립), 고객·이벤트 후보(자동 연결 못 했을 때), 전사 원문.

- 전사 원문은 받은 파일(또는 전사 결과 파일)을 코드가 그대로 읽어 `전사 원문 (N줄)` 접기 제목 아래에 끝까지 붙인다. 계좌·카드번호만 가림 (D42).
- 녹음 클립: 근거 줄마다 그 구간(앞뒤 1초, 최대 30초)을 잘라 줄 밑에 재생 버튼으로. 계좌·카드번호를 가린 근거는 자르지 않음. 고객 음성이 노션에 저장되므로 프로필 `.env`의 `SAGAK_AUDIO_CLIPS=1`일 때만 (D43).
- 봇 테스트: 성함 `[테스트] …` 또는 연락처 `010-0000-…` 고객은 테스트 기록. 점검은 테스트끼리만, `sagak cleanup-test`로 한꺼번에 휴지통 (D44). 시나리오는 `docs/bot-test-scenarios.md`.

## 연결 규칙

1. **연락처와 이름이 모두 같으면** 같은 고객으로 자동 연결. 고객 페이지에서 그 고객의 과거·현재 이벤트가 모두 보임.
2. 연락처는 같은데 이름이 다르면(가족이 대신 연락 등) 연결하지 않고 `고객 연결 필요`. 이름만 같으면 후보로만 표시.
3. 그 고객의 진행 중 이벤트(상담진행중 · 추후연락 · 이벤트진행예정) 중 **테마가 같은(또는 미정인) 이벤트가 하나**면 거기에 다음 차수 상담으로 추가. 테마가 다르면 새 이벤트.
4. 진행 중 이벤트가 없으면 새 이벤트. **둘 이상**이면 연결하지 않고 `고객 연결 필요`로 후보를 보여줌.
5. `고객 연결 필요`로 남은 상담은 직원이 봇에 "같은 고객/별도 고객"으로 답하면 `sagak resolve`가 연결하고 제목·차수·검토 상태를 정리한다. 고객 이름은 바꾸지 않는다.
6. 이벤트·고객의 기존 값은 새 입력에 없다는 이유로 지우지 않음. 값이 다르면 덮어쓰지 않고 상담 이력에 표시.

## 자동 점검 (D41)

봇이 상담을 기록할 때마다 모든 이벤트를 점검합니다(`sagak sweep`, 따로 실행도 가능).

1. 결제 상태 `예약금 입금` + 확정 일시 비어 있음 → 확정 일시를 희망 일시로.
2. 결제 상태 `예약금 입금` + 이벤트 상태 상담진행중·추후연락 → `이벤트진행예정`.
3. `이벤트진행예정` + 확정 일시 날짜가 오늘(한국 시간) 이전 → `이벤트완료`.
4. 희망 일시가 00:00인데 원문에 시각이 있음 → 고치지 않고 답장에서 알림.

이벤트취소·이벤트완료는 점검하지 않습니다. 취소된 이벤트는 캘린더(이달의 이벤트·홈 캘린더)에 나오지 않고, 확정 일시 값은 기록으로 남깁니다 (D50).

고친 이벤트는 페이지 본문 `자동 정리 (MM/DD HH:MM)`에 바꾼 내용과 이유가 남고, 텔레그램 답장에 한 줄씩 나옵니다.
기록 전에는 그 고객의 이전 상담 전체를 읽고(`sagak history`), 노션에 비어 있는 이벤트 칸을 이전 상담 내용으로 보충합니다.

## 함께 보기 (Notion 설정)

- 고객 페이지: 상단에 고객 구분·연락처·이벤트 수, 아래에 그 고객의 **이벤트 목록**이 바로 보임.
- 이벤트 페이지: 상단에 고객·이벤트 상태·희망 일시, 아래에 **1차·2차 상담 이력**이 바로 보임.
- 상담 이력에는 이벤트를 거쳐 **고객 이름이 자동 표시**됨(롤업).
- 금액 속성(고객 예산, 예약금액, 확정 금액, 옵션 가격)은 세 자리마다 쉼표로 표시.
- 보기: 이벤트 DB의 `이달의 이벤트`(캘린더), 상담 이력 DB의 `확인 대기`(직원 검토 목록).
- 위치: 사각사각 워크스페이스 › 팀스페이스 홈 › `사각사각 고객 보드 (검토용)`. 현재 가상 데이터 2명·3건·3회 상담이 들어 있음.
- DB ID 같은 값은 코드에 넣지 않고 sagak profile 설정에서 읽음.

## 범위 밖

기존 관리 페이지에 자동 입력, 결제 처리, 통계·캘린더 외 화면.
